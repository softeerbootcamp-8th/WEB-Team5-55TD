# 실시간 경매 WebSocket 문제 해결 기록

## 1. 해결하려던 문제

실시간 경매 화면은 다른 사용자의 입찰이 확정되면 현재가와 입찰 내역을 빠르게 보여줘야
한다. 입찰 요청 자체는 기존 REST API로 처리할 수 있지만, 다른 사용자의 화면은 요청을
보내지 않으므로 서버가 변경 사실을 먼저 알려 줄 통로가 필요했다.

WebSocket을 연결하는 것만으로 이 요구사항이 끝나지는 않았다. 애플리케이션이 여러 대이면
각 서버가 관리하는 WebSocket 연결이 서로 분리되고, Redis Pub/Sub과 WebSocket은 장애 중
메시지를 보관하거나 다시 전달하지 않는다. 트랜잭션이 끝나기 전에 알림을 보내면 실제로는
rollback된 입찰이 화면에 나타날 수도 있다.

따라서 이 작업의 목표를 단순한 실시간 전송이 아니라 다음 두 가지로 나눴다.

- 정상 상황에서는 확정된 입찰을 즉시 전달한다.
- 일부 알림을 잃더라도 화면이 결국 DB의 최신 상태로 돌아오게 한다.

DB를 최종 상태의 원천으로 두고, WebSocket은 빠른 알림 경로, REST 조회는 유실 복구 경로로
역할을 분리했다.

## 2. 실제 메시지 흐름

입찰자는 `POST /auctions/{auctionId}/bids`로 입찰한다. 서버는 경매 행을 잠그고 입찰가를
검증한 뒤, 이전 최고 입찰과 새 입찰, 경매의 현재가를 하나의 트랜잭션에서 변경한다.

트랜잭션이 commit되면 입찰 갱신 이벤트가 Redis Pub/Sub으로 발행된다. 모든 애플리케이션
인스턴스는 같은 Redis 채널 패턴을 구독하고 있으므로 이벤트를 받는다. 각 인스턴스는 받은
이벤트를 자신이 관리하는 `/topic/auctions/{auctionId}` 구독자에게 전달한다.

브라우저는 화면에 들어오면 `/api/ws`로 STOMP 연결을 맺고 해당 경매 Topic을 구독한다.
구독이 확인된 뒤 DB 상태를 다시 조회하며, 이후에도 일정 간격으로 조회한다. 따라서
WebSocket 메시지를 놓쳐도 화면은 다음 조회에서 최신 가격과 입찰 내역을 다시 확인한다.

## 3. 다중 인스턴스에서 일부 사용자만 갱신되는 문제

Spring Simple Broker는 애플리케이션 프로세스 안에 존재한다. 애플리케이션 A에 연결된
브라우저의 session과 subscription을 애플리케이션 B는 알 수 없다. B가 입찰 요청을 처리한
뒤 자신의 Simple Broker에만 메시지를 보내면 A에 연결된 사용자는 갱신을 받지 못한다.

이 문제는 Sticky Session으로 해결되지 않는다. Sticky Session은 한 브라우저의 연결을 같은
서버에 유지할 뿐, 입찰 REST 요청을 처리한 서버와 다른 서버의 WebSocket 구독 정보를
공유하지 않는다.

그래서 Redis Pub/Sub을 인스턴스 사이의 fan-out 통로로 사용했다. 입찰을 처리한 서버는
특정 인스턴스에 직접 WebSocket 메시지를 보내지 않고 Redis에 한 번만 발행한다. 모든
인스턴스가 이벤트를 받은 뒤 자기 로컬 구독자에게 전달한다. 이 구조에서는 입찰 처리 서버와
WebSocket 연결 서버가 달라도 같은 경매의 사용자가 모두 갱신을 받을 수 있다.

로컬 WebSocket 전송과 Redis 발행을 동시에 유지하는 방법도 검토할 수 있지만, 발행 서버에
연결된 사용자만 같은 이벤트를 두 번 받을 수 있다. 전파 경로를 Redis 하나로 통일해 중복
경로 자체를 만들지 않았다.

## 4. rollback된 입찰이 화면에 보이는 문제

입찰 저장 직후 트랜잭션 안에서 Redis나 WebSocket으로 메시지를 보내면, 외부 전송 이후 DB
commit이 실패할 수 있다. 이 경우 브라우저에는 성공한 것처럼 보이지만 DB에는 존재하지 않는
입찰이 된다. 이미 전송된 메시지는 DB rollback으로 취소할 수 없다.

입찰 서비스는 트랜잭션 안에서 Spring 이벤트만 등록하고, 실제 Redis 발행은
`AFTER_COMMIT` 단계에서 실행한다. commit에 실패하면 listener가 실행되지 않으므로 Redis와
WebSocket에도 아무 메시지가 전달되지 않는다.

이 선택으로 실시간 알림의 기준을 "입찰 로직이 실행됨"이 아니라 "입찰이 DB에 확정됨"으로
맞췄다. WebSocket은 트랜잭션 결과를 결정하지 않고 확정된 결과만 전달한다.

## 5. Redis 또는 WebSocket에서 마지막 메시지를 잃는 문제

Redis Pub/Sub은 구독 중인 소비자에게만 메시지를 전달한다. Redis 연결이 잠시 끊기거나
애플리케이션이 재시작되면 그 시간에 발행된 메시지를 나중에 다시 받을 수 없다. DB commit
직후 프로세스가 종료되어 Redis 발행이 실행되지 않는 경우도 있다. 브라우저 WebSocket이
연결된 상태여도 서버 내부 전파만 실패하면 사용자는 실패를 알 수 없다.

이 알림을 유실 불가능하게 만들기 위해 Outbox와 영속 메시지 큐를 사용할 수도 있다. 하지만
화면 갱신 알림은 정산 이벤트와 달리 모든 중간 메시지를 반드시 재생할 필요가 없다. 오래된
가격 변화를 차례로 재생하는 것보다 현재 DB 가격을 한 번 다시 읽는 편이 목적에 맞다.

따라서 진행 중인 경매 화면은 WebSocket 연결 여부와 별개로 REST 조회를 유지한다. 활성
화면은 약 15초마다 조회하며, 각 클라이언트에 작은 무작위 지연을 더해 같은 시각에 요청이
몰리지 않게 한다. 숨겨진 탭은 조회 간격을 약 60초로 낮추고, 다시 활성화되면 즉시 조회한다.

WebSocket은 정상 상황의 즉시성을 담당하고 polling은 장애 후 최종 수렴을 담당한다. 이
구조는 알림 유실 자체를 없애지는 않지만, 정상적인 활성 화면에서는 최대 약 한 polling
주기 안에 DB 상태로 복구한다.

## 6. 최초 연결과 재연결 경계에서 이벤트를 놓치는 문제

화면이 REST 상태를 먼저 조회하고 나중에 Topic을 구독하면 두 작업 사이에 확정된 입찰을
놓칠 수 있다. Redis Pub/Sub은 과거 이벤트를 다시 보내지 않기 때문에 연결이 완료되어도 그
입찰은 도착하지 않는다.

이를 줄이기 위해 STOMP 구독 요청에 receipt를 사용한다. Broker가 구독 등록을 처리했다고
응답한 뒤 경매 상세와 최신 입찰을 즉시 다시 조회한다. 화면 loader가 먼저 가져온 데이터는
초기 렌더링에 사용하되, 구독 이후의 조회가 연결 전후 공백을 다시 확인한다.

서버 재시작이나 네트워크 전환으로 다시 연결된 경우에도 같은 순서를 반복한다. 재연결,
Topic 재구독, 구독 확인, REST 재조회가 하나의 복구 과정이다. 재연결만 수행하면 끊긴 동안의
Redis 메시지는 복구되지 않기 때문이다.

## 7. 중복 메시지와 순서 역전 문제

같은 이벤트가 네트워크나 전파 계층에서 중복될 수 있고, 서로 다른 연결 경로의 지연으로
과거 메시지가 나중에 도착할 수 있다. 현재가에 증가분을 더하는 방식으로 처리하면 중복
메시지 한 건만으로도 실제 DB보다 높은 가격이 만들어진다.

서버는 메시지에 `eventId`와 최신 입찰의 `bidId`를 함께 제공한다. 같은 `eventId`를 이미
처리했다면 동일 이벤트의 중복으로 판단한다. 같은 경매에서 새 `bidId`가 현재 알고 있는
번호보다 작거나 같으면 과거 또는 중복 입찰로 보고 화면에 적용하지 않는다.

유효한 이벤트도 가격 차이를 계산하지 않는다. 서버가 확정한 `currentPrice` 절대값으로
교체한다. 이렇게 하면 같은 결과를 다시 받아도 화면 상태가 달라지지 않는다.

`bidId`는 모든 경매가 공유하는 자동 증가 값이므로 번호 사이의 공백만으로 유실을 판단하지
않는다. 다른 경매의 입찰이나 rollback 때문에 번호가 건너뛸 수 있다. 비교는 같은 경매에서
받은 메시지의 선후 관계를 판단하는 용도로만 사용한다.

## 8. 늦은 REST 응답이 최신 WebSocket 가격을 덮는 문제

REST 조회를 시작한 뒤 응답이 오기 전에 더 최신 WebSocket 이벤트를 받을 수 있다. 조회
응답을 무조건 화면에 적용하면 잠시 최신 가격을 보여준 뒤 과거 가격으로 되돌아간다.

현재 백엔드에는 문서에서 설계했던 `latestBidId` 포함 전용 snapshot API가 없다. 실제
구현에서는 경매 상세 API와 최신순 입찰 목록 API를 함께 사용한다. 최신 입찰 목록의 첫 번째
`bidId`를 가장 최근 번호로 보고, 이미 처리한 WebSocket 입찰보다 오래된 결과는 최신 번호를
되돌리지 못하게 한다. 현재 경매의 입찰가는 성공할 때마다 증가하므로 늦은 상세 응답의 낮은
가격도 최신 가격을 덮지 못하게 한다.

두 REST API는 하나의 DB read transaction에서 만들어진 원자 snapshot이 아니다. 요청 사이에
새 입찰이 생기면 가격과 입찰 목록이 잠시 다른 시점을 나타낼 수 있다. 다음 WebSocket
메시지나 polling에서 다시 수렴하지만 엄격한 한 시점의 일관성은 보장하지 않는다. 이 보장이
필요해지면 백엔드가 `latestBidId`와 화면 상태를 한 응답으로 제공해야 한다.

## 9. 서버 장애 시 재연결 요청이 한꺼번에 몰리는 문제

배포나 장애로 서버가 재시작되면 많은 브라우저 연결이 동시에 끊긴다. 모든 브라우저가 즉시
같은 간격으로 재시도하면 복구 중인 서버에 WebSocket handshake와 REST 요청이 한꺼번에
몰린다.

재연결 간격은 실패할 때마다 늘어나는 지수 backoff를 사용하고 최대 30초로 제한한다. 첫
재시도 시점에는 클라이언트마다 무작위 지연을 더한다. backoff는 장애가 길어질 때 요청량을
줄이고, 무작위 지연은 여러 브라우저의 재시도 시점을 분산한다.

연결이 복구되면 Topic을 다시 구독하고 즉시 DB 상태를 조회한다. 화면을 떠나면 연결과
재연결 작업을 종료해 더 이상 필요하지 않은 경매가 백그라운드에서 계속 재시도하지 않게
한다.

## 10. 끊어진 연결을 늦게 발견하는 문제

TCP 연결은 네트워크가 단절되어도 양쪽이 즉시 알지 못할 수 있다. 중간 프록시가 유휴 연결을
정리할 수도 있다. 화면에는 연결된 것처럼 보이지만 실제 메시지는 오지 않는 유령 연결이
남을 수 있다.

서버와 브라우저는 10초 heartbeat를 사용한다. 일정 시간 heartbeat를 받지 못하면 STOMP
클라이언트가 연결 실패를 감지하고 재연결 절차를 시작한다. heartbeat는 데이터 변경을
전달하는 메시지가 아니라 연결이 실제로 살아 있는지 확인하는 신호다.

## 11. WebSocket 연결이 새로운 입력 경로가 되는 문제

WebSocket endpoint를 열면 클라이언트가 임의의 STOMP 명령과 destination을 보낼 수 있다.
경매 화면은 서버에서 클라이언트로 확정 상태를 전달하는 기능만 필요하므로 클라이언트가
가짜 입찰 메시지를 `SEND`할 이유가 없다.

백엔드는 허용할 STOMP 명령을 제한하고 `SEND`를 차단한다. 구독 destination도
`/topic/auctions/{양수 ID}` 형식만 허용한다. WebSocket handshake의 Origin은 설정된
프론트엔드 주소로 제한한다. 브라우저가 받은 채널과 역직렬화된 이벤트의 경매 식별자가
일치하는지도 확인해 잘못된 채널로 들어온 이벤트를 전달하지 않는다.

입찰은 계속 REST API로만 받는다. REST 경로에 이미 존재하는 인증, 요청 검증, 오류 응답과
트랜잭션 규칙을 그대로 사용하고 WebSocket에 별도의 요청·응답 규약을 만들지 않았다.

## 12. 다른 대안을 선택하지 않은 이유

Polling만 사용하면 구조는 단순하고 Redis 장애의 영향을 받지 않지만, 정상 상황에서도 최대
polling 주기만큼 현재가 반영이 늦다. 실시간 경매에서 정상 흐름의 지연을 받아들이기 어려워
주 경로로 선택하지 않았다.

WebSocket만 사용하면 요청량은 줄지만 마지막 이벤트를 잃었을 때 화면이 틀렸다는 사실을
발견할 방법이 없다. 연결이 살아 있다는 사실은 모든 메시지를 받았다는 보장이 아니므로
REST 복구 경로를 함께 유지했다.

외부 STOMP Broker Relay는 인스턴스 간 구독과 메시지 전달을 Broker에 맡길 수 있지만, 현재
규모에서는 별도 Broker 운영과 설정 복잡도가 커진다. 기존 Simple Broker와 Redis를 유지하는
편이 변경 범위가 작았다.

Outbox와 메시지 큐는 유실 불가능한 정산 이벤트에 적합하다. 화면 알림은 중간 변화를 모두
재생하는 것보다 최신 DB 상태로 수렴하는 것이 중요하므로 polling 복구가 더 단순하다.

SockJS는 native WebSocket이 차단된 환경까지 지원할 때 유용하지만, 현재 대상 브라우저와
CloudFront는 native WebSocket을 지원한다. 확인되지 않은 호환 요구를 위해 fallback 규약과
추가 의존성을 도입하지 않았다.

## 13. 현재 보장과 남은 한계

현재 구현은 commit된 입찰만 방송하고, 여러 애플리케이션 인스턴스에 연결된 사용자에게 같은
결과를 전달한다. 중복·과거 입찰은 화면 상태를 되돌리지 않으며, 연결이나 Redis 알림이
끊겨도 주기적인 REST 조회로 최신 DB 상태에 수렴한다.

다만 Redis Pub/Sub과 WebSocket의 메시지 replay는 제공하지 않는다. 유실된 중간 화면 변화는
복원하지 않고 최신 상태만 복구한다. 복구 시간은 polling 간격과 브라우저 background timer의
영향을 받는다.

또한 현재 WebSocket 공개 이벤트는 입찰 갱신만 구현되어 있다. 경매 시작과 종료 상태는
REST 조회에서 확인하며, 전용 realtime snapshot API도 아직 없다. 전체 경매 상태의 엄격한
순서와 원자 snapshot이 요구되면 경매별 상태 version과 `latestBidId`를 한 응답에 포함하는
백엔드 계약을 추가로 검토해야 한다.
