# 동기 비관적 락 vs 비동기 입찰 접수 부하 테스트

- 실행일: 2026-08-12 (KST)
- 대상 버전: `main` `0ecb0f2e55f2de4e232769b5222f79dd9f100a0f`
- 환경: production-like 단일 `t3.small` (2 vCPU, 2 GiB), Hikari maximum pool size 10, connection timeout 5초
- 관련 버그: OOTD-465
- 수정 PR: #205

## 결론

`bid_request.auction_id`의 외래키를 제거하면 비동기 접수 경로를 경매 행 비관적 락으로부터 분리할 수 있다. 가장 직접적인 12초 행 락 재현에서 비동기 요청 40건의 HTTP 성공률은 25%에서 100%로 증가했고 Hikari pending은 31에서 0으로 감소했다.

일반 부하에서도 비동기 방식은 200 VU 고정 부하에서 Hikari active 최대 3, pending 0을 유지했다. 같은 조건에서 동기 방식은 active 10, pending 7까지 도달했다. Burst 300에서는 비동기 접수 p95가 1.18초로 동기 2.04초보다 42.2% 낮았다.

다만 비동기 방식은 HTTP 접수 완료와 실제 입찰 처리 완료가 분리된다. Fixed-load 2,000건의 HTTP p95는 1.31초였지만 SQS 처리까지의 end-to-end p95는 22.16초였다. 따라서 비동기는 커넥션 풀과 사용자 요청을 보호하지만, 처리량을 무한히 늘리는 방식은 아니다. 큐 적체 시간과 최종 결과 알림을 별도 SLO로 관리해야 한다.

## 가설

1. 동기 비관적 락 방식은 경합 중 트랜잭션이 JDBC 커넥션을 점유하므로 동시성이 증가하면 Hikari active/pending이 풀 한도까지 상승한다.
2. 비동기 접수는 짧은 `bid_request + outbox` 트랜잭션만 수행하므로 HTTP 레이턴시와 커넥션 점유를 제한할 수 있다.
3. 기존 `fk_bid_request_auction`은 INSERT 무결성 검사 과정에서 부모 `auction` 행의 공유 락을 요구하므로 가설 2의 격리를 깨뜨린다.
4. 외래키를 제거해도 애플리케이션의 경매 존재 검증과 SQS FIFO의 경매별 message group을 유지하면 최종 입찰 결과는 일관되고 순차적으로 처리된다.

## FK 락 원인 대조 실험

동일 경매 행을 `SELECT ... FOR UPDATE`로 12초간 잠근 뒤 비동기 접수 요청 40건을 동시에 전송했다.

| 조건 | HTTP 결과 | 평균 | p95 | Hikari active | Hikari pending |
| --- | ---: | ---: | ---: | ---: | ---: |
| `fk_bid_request_auction` 존재 | 202 10건 / 500 30건 | 6.86초 | 12.02초 | 10 | 31 |
| 외래키 제거 | 202 40건 / 500 0건 | 591ms | 657ms | 1 | 0 |

외래키 제거 후에도 실제 입찰 처리 완료는 경매 행 락 해제까지 평균 약 11.76초 기다렸다. 즉 접수 트랜잭션과 커넥션 풀은 격리됐지만 실제 입찰의 직렬 처리는 유지됐다.

## 시나리오

| 시나리오 | 정의 |
| --- | --- |
| Burst | 300 VU가 총 300 POST를 동시에 한 번씩 전송 |
| Fixed-load | 200 VU가 초당 한 번씩 10초간 전송, 총 2,000건 |
| Ramp-to-break | 20 → 50 → 100 → 200 → 300 → 400 VU 단계별 동시 요청 |

동기 API는 `POST /auctions/{id}/bids`, 비동기 API는 `POST /auctions/{id}/bid-requests`를 사용했다. 각 방식은 서로 다른 진행 중 경매를 사용했고 동일 가격의 동시 입찰을 보냈다. 동기의 409는 비관적 락 이후 가격 규칙을 재검증한 정상 업무 거절이며, 비동기의 202는 접수 성공이다. 비동기의 최종 성공/실패는 `bid_request` 상태로 별도 확인했다.

## HTTP 결과

### Burst 300

| 방식 | HTTP 결과 | 처리량 | 평균 | p95 | p99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 동기 | 201 1건 / 409 299건 | 126.44 RPS | 1,052.60ms | 2,035.06ms | 2,291.62ms |
| 비동기 | 202 300건 | 186.27 RPS | 604.40ms | 1,175.25ms | 1,236.60ms |

비동기는 동기 대비 처리량이 47.3% 높았고 평균 레이턴시는 42.6%, p95는 42.2% 낮았다.

### Fixed-load 200 VU, 10초

| 방식 | HTTP 결과 | 처리량 | 평균 | p95 | p99 | 최대 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 동기 | 201 1건 / 409 1,999건 | 198.86 RPS | 410.67ms | 1,396.89ms | 2,092.52ms | 3,246.77ms |
| 비동기 | 202 2,000건 | 189.32 RPS | 432.54ms | 1,309.26ms | 4,399.78ms | 7,398.29ms |

비동기 p95는 동기보다 6.3% 낮았지만 p99와 최대값은 더 컸다. 따라서 비동기가 모든 구간에서 HTTP tail latency를 개선한다는 가설은 기각한다. 핵심 개선점은 커넥션 풀 격리와 접수 성공률이다.

### Ramp-to-break

| VU | 동기 p95 | 비동기 p95 | 동기 결과 | 비동기 결과 |
| ---: | ---: | ---: | ---: | ---: |
| 20 | 276ms | 91ms | 201 1 / 409 19 | 202 20 |
| 50 | 210ms | 154ms | 409 50 | 202 50 |
| 100 | 375ms | 372ms | 409 100 | 202 100 |
| 200 | 947ms | 1,137ms | 409 200 | 202 200 |
| 300 | 1,270ms | 1,221ms | 409 300 | 202 300 |
| 400 | 1,365ms | 1,384ms | 409 400 | 202 400 |

400 VU까지 양쪽 모두 HTTP 5xx, 전송 실패, 429가 없었다. 이 범위에서는 명확한 오류 임계점을 찾지 못했다. 300~400 VU에서는 테스트 실행기와 단일 인스턴스의 CPU/소켓 스케줄링 영향이 커져 두 방식의 HTTP p95가 약 1.2~1.4초로 수렴했다.

## Datadog / Hikari 결과

관측 주기가 짧은 Burst와 Ramp의 순간 피크를 놓칠 수 있어, 풀 고갈 비교는 10초 Fixed-load와 12초 강제 락 실험을 중심으로 판단했다.

| 시나리오 | 방식 | Hikari active 최대 | pending 최대 | idle 최소 | connection timeout |
| --- | --- | ---: | ---: | ---: | ---: |
| 강제 행 락 12초, FK 존재 | 비동기 | 10 | 31 | 0 | 발생 |
| 강제 행 락 12초, FK 제거 | 비동기 | 1 | 0 | 8 이상 | 0 |
| Fixed-load | 동기 | 10 | 7 | 0 | 0 |
| Fixed-load | 비동기 | 3 | 0 | 7 | 0 |

Fixed-load 전체 구간에서 호스트 CPU user 최대 63.0%, system 최대 7.6%, 가용 메모리 최소 21.2%였다. Swap 사용량은 약 118~127 MiB였고 증가가 일부 있었지만, 이번 비교에서 HTTP 실패와 직접 연결되는 swap-in/out 증거는 없었다.

## 비동기 최종 처리와 순서 검증

| 시나리오 | 접수 | 최종 성공 | 최종 업무 실패 | Pending | E2E 평균 | E2E p95 | E2E 최대 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Burst 300 | 300 | 1 | 299 | 0 | 2.56초 | 4.12초 | 4.29초 |
| Fixed-load | 2,000 | 1 | 1,999 | 0 | 13.33초 | 22.16초 | 22.63초 |
| Ramp 합계 | 1,070 | 1 | 1,069 | 0 | 2.04초 | 4.45초 | 4.97초 |

- 각 경매에서 실제 `bid` 행은 정확히 1건만 생성됐다.
- `bid.bid_request_id` 중복은 없었다.
- Outbox 생성 순서를 기준으로 `processed_at` 역전은 세 시나리오 모두 0건이었다.
- 테스트 종료 후 outbox unpublished 0건, SQS visible/in-flight 0건, `bid_request` pending 0건을 확인했다.
- 단순 `bid_request_id` 순서와 `processed_at`을 비교하면 역전처럼 보이는 행이 있었으나, 동시 INSERT의 auto-increment 할당 순서는 커밋/Outbox 전송 순서를 의미하지 않는다. 실제 전송 기준인 Outbox 순서로 검증해야 한다.

따라서 동일 경매의 메시지가 FIFO message group으로 순서대로 처리되고 최종 상태가 모두 종결된다는 가설은 이번 데이터에서 성립했다.

## 판단

외래키 제거를 포함한 비동기 방식은 다음 목표를 충족한다.

1. 경매 장기 락이 HTTP 접수 트랜잭션의 커넥션을 붙잡는 경로를 차단한다.
2. 지속 부하에서 Hikari pending을 0으로 유지해 다른 API로의 풀 고갈 전파를 방지한다.
3. Burst에서 접수 레이턴시와 처리량을 유의미하게 개선한다.
4. SQS FIFO와 멱등 키를 통해 동일 경매의 최종 입찰 결과를 순차적이고 일관되게 종결한다.

다음 운영 지표를 별도 SLO로 두는 것이 필요하다.

- HTTP 접수: p95, p99, 5xx, Hikari pending/timeout
- 비동기 완료: `bid_request.created_at → processed_at` p95/p99
- 적체: SQS visible/oldest age, outbox unpublished/oldest age
- 정합성: pending 장기 체류, 하나의 경매에 복수 성공 입찰, `bid_request_id` 중복

Fixed-load에서 최종 처리 p95가 22초까지 늘었으므로, 사용자 UI는 202를 최종 성공으로 표현하면 안 된다. 접수 상태를 명확히 표시하고 WebSocket/REST 보정으로 최종 성공 또는 실패를 전달해야 한다.

## 제한 사항

- 동기와 비동기의 HTTP 상태 의미가 다르므로 201/409와 202를 같은 성공률로 직접 비교할 수 없다.
- 동일 가격을 사용해 한 요청만 성공하도록 한 테스트다. 서로 증가하는 가격, 다중 회원, 여러 경매가 섞인 트래픽은 별도 검증이 필요하다.
- 부하 생성기는 단일 외부 호스트의 Python thread pool이므로 300~400 VU 결과에는 클라이언트 측 스케줄링 영향이 포함된다.
- 운영과 같은 단일 인스턴스에서 수행했으므로 테스트 구간의 실제 사용자 트래픽이 완전히 배제되지는 않았다.
